---
name: quantify
description: You're about to answer a question about the site's traffic or the deployment with a count, a rate, a cost, or its health.
---

Questions come in the operator's words — visitors, sessions, pageviews, engagement, cost — and the answer goes back in them. The machinery has its own words — slice, birth, chunk, ping, drain, page context — for how the measuring happens. Use one where the answer needs it, and define it in plain terms the first time it appears ("a page context — one open tab on one page; a birth — the recorder starting up in it, before anything is captured yet"). The operator knows their sites as domains, not snippet ids; `locus status` lists the hosts each snippet's recordings opened on.

Lead with the answer: the number or the verdict in the first line, what bounds it next, the method after that. Size it to the question — if two numbers were asked, answer two numbers, with their caveats. Whatever you computed on the way (a daily series, a distribution, the files you read, the scripts and logs you wrote) stays with you unless the operator's decision turns on it. Don't say "normal", "healthy", or "typical" unless you can name what you measured against.

Session, engaged, and bounce mean what the operator declared in `config/definitions.toml`, and the db's `sessions` table is that declaration applied to the recordings. Read the file before any behavior question. Adjusting a meaning is a knob change (the change-deployment skill).

Structure is a query; content is a read. A count that is a function of what happened — which pages, which inputs, in what order, how many, how long — comes off the flat columns and the tables here. A count that turns on what the visitor saw or what something meant — how many visitors saw the error, how many bought — requires reading the recordings: whittle to the candidates by structure, read them with the model (the analyze-recordings skill), then count.

## Which plane answers which question

- **AE (Cloudflare Analytics Engine) — rates.** The worker's fire-and-forget datapoints. They are sampled at volume, so a rate is an estimate: `sum(_sample_interval)` is the true count, never `count()`, and `locus ae` reports the dataset's sampling state with every result. Sampling is stamped on the row — under load, datapoints land with `_sample_interval` above 1. The widest `_sample_interval` in a result tells you what the read is standing on, and narrowing the query buys certainty only where that value drops. Because an AE denominator is an estimate, a ratio against R2's exact figures can drift slightly past 1.0. `locus ae "<sql>"` passes SQL to the deployment's dataset and self-serves the account, so you compose SQL, not HTTP. With no `CAPTURE` binding, AE is off and there is no rates plane: `locus ae` fails loud (the SQL API errors on an account or dataset that never wrote) or returns empty once an old dataset drains, and every answer falls back to R2.
- **R2 — exact, not sampled.** The chunk objects: arrivals, storage bytes, operation counts. `locus ls` returns one row per slice — snippet, visitor, slice id, when it opened, its chunks and bytes, when those landed, and against a loaded db whether it is loaded, or past the retention horizon and never loadable — at any scale, scoped by key prefix. The prefix — any leading substring of the key — is the whole query language, and the key layout lives in `store/src/keys.js`; read it before composing one. A date-partition prefix is cheap. A bare snippet prefix is a full scan. Any scope that is not a prefix is your own filter over the rows, which arrive in whatever order the store gives them up. The rows carry the snippet, visitor, and slice that join an arrival to a birth, so completeness is a join you compose.
- **CF usage analytics — metering.** Worker requests, R2 storage and operations. `locus usage "<graphql>"`; the account self-serves and binds to `$account`. Usage numbers, never dollars.
- **The loaded db — exact, and only what was loaded.** `locus load` brings a prefix of the store into `data/events.db`. Every count over it is of recordings that shipped and were loaded, never of the site's traffic, and a visitor whose earlier slices sit outside the loaded range is only partly there. It is the store as of the last load, and a window loaded earlier has changed since — chunks arrive late by design — so load it again before counting. Sessions, engaged, and bounce live here: `sessions` holds one row per session under the operator's definition, and every event carries the session that held it (`events.session_id`), so a count is `count(*)` and a cut is a join to `slices` or `events`. The `engaged` column is a verdict, not testimony — the operator's numbers applied, re-derived when they change. A disputed verdict has three supports (the definition, the recording it ran over, the derivation), and working out which one gave way is the adjudicate skill. Read the live schema (`sqlite3 data/events.db '.schema'`) before querying; the column comments say what each holds.

## A query names positions, never fields

AE rows are positional (`index1`, `blob1..N`, `double1..N`): a query names positions, never field names, and what the recorder puts on the wire is not a selectable column. `store/src/telemetry-schema.json` declares which position is which — the one layout the worker writes rows by. `store/src/telemetry.js` owns each field's meaning and validation, and `store/wrangler.toml` names the dataset a query reads FROM. Read them before composing a query; none of it is restated here.

**Two clocks, two facts.** Every row carries its server-receive `timestamp`: true time, when the datapoint verifiably reached ingestion. A row the recorder sent also carries the device's own client-minted stamp (telemetry-schema.json says where each metric carries it; a custom sink that omits the stamp lands the unmeasured sentinel). The metrics the worker mints about itself — the rejections and its own errors — have only the one clock, and it is the right one, because they happen at ingestion. The client clock is the recording's clock: events, slice ids, and the R2 date partition are all minted on it. So anything that correlates with the recording reads client time, and true-time questions read server time. Pick one per question and never subtract across them. A device's clock can run hours wrong, so server minus client mixes transit with skew — it is not latency — and aggregating many devices on their client clocks inherits every device's skew. Slice ids and the R2 date partition are minted on the device's clock too: a skewed device files its slices under its own clock's day on both planes, and a listing's max open time can sit ahead of now. One reflex to catch: AE's indexed `timestamp` is the natural WHERE column, so queries window on server time by habit. Fine as a query bound; wrong as the moment the row reports when the answer joins to the recording.

**One question, one query.** Numbers from queries with different WHEREs never combine. The dialect evaluates `if()` inside aggregates, so several scopes can compute in one query against one FROM and one WHERE; a subquery is legal in `FROM` and refused in `IN`, so a per-entity membership read is GROUP BY with HAVING, aggregated again in an outer SELECT when the question needs it. It is a small dialect: no `domain()` or `uniq()`, no single quote inside a string literal, escaped or doubled (a value carrying one is matched with `LIKE` and `_` in its place), `position()` wants `IN`, `if()` wants both branches the same type (`0.0` against a double column), no aggregate takes a string (a per-group string is a GROUP BY key), and the SQL body caps at 10,000 characters — so a host cut over urls is `LIKE` per host, a large `IN (...)` list of ids is over the cap and rewrites as GROUP BY on the cohort's own dimensions, and a failed parse names what it did not understand. A rate compared across windows holds clock hours fixed: across unequal windows the diurnal shape reads as a trend. And a window meaning "from t" wants `timestamp >= toDateTime(t)` — `>` silently excludes the rows stamped within t's own second.

## A zero is a diagnosis, not a measurement

An answer on this plane carries no evidence of its own correctness — a query that cannot fail proves nothing by succeeding — so give every load-bearing number a check independent of the read that produced it. An absent row is not an absent ping:

- **A ping the worker bounced.** The worker gates every ping's shape and records what it refused as `telemetry_rejected`, with the reason. Any of those rows means some device's pings are missing from every count you take here — read them before trusting a rate.
- **A device without the channel.** The ping transport assesses itself per environment and takes whichever of its two carriers gets through (`recorder/src/sink.js`; a `transport_probe` row attests a delivered beacon from that context). Losing a device outright takes a block that eats both — typically a blocker rule on the telemetry path itself. Such a device's chunks keep arriving — it is fully present on the content plane, device facts included — while its pings never existed. This plane is then missing whole devices, not rows: visitor and session counts undercount by an audience-dependent share, and arrivals ÷ births reads above 1.0, a floor on delivery, never completeness.
- **A row sampling dropped.** Enumerated absence is not absence: a visitor missing from an enumerated or joined set may have lost its only row to the sampler. Treat the set as a sample of the population, never a census.
- **A window older than the horizon.** The recordings plane reaches back exactly as far as the retention horizon and no further: a question about a month past it reads a clean zero from a db that once held the answer. Check the span the question asks for against the horizon before reading its emptiness as behavior. AE has its own retention, and it bounds the rates plane the same way.
- **A lull.** Births go quiet on their own, and an empty fresh window looks like capture that stopped. Measure the silence against the site's longest same-clock-hour gap over the prior week before reading it as a stop; a gap that clears that spread earns a mechanism read — a drive under a fresh cookie, the served bundle's bytes, the config endpoint's answer. A fault or gate row from a new page context proves the script still runs.
- **An identifier that never existed.** A typo or a shortened id returns the same clean zero as real absence. Equality wants the full id; `LIKE 'prefix%'` matches everything a prefix abbreviates. Before reading any identifier-scoped zero as absence, confirm the identifier matches anything across full retention. The FROM is an identifier too: AE answers a query against a dataset that never wrote with the same zero-shaped result, and the worker's binding name is not the dataset — `store/wrangler.toml` names what a query reads FROM.

## Is it recording at all?

Binary, and the cheapest check. A key under the snippet's R2 prefix proves the whole chain: the script loaded, recorded, and uploaded. A `slice_started` row proves only that the script loaded and the recorder started — the birth fires when the page context opens, before there is a DOM to capture, on a channel separate from the upload. `page_load` fires on the first snapshot, and is the ping that proves something *replayable* exists.

The check itself mints a visitor: driving the site yourself lands in both planes, indistinguishable from traffic. Note the visitor identity you drove under and exclude it from every organic read after.

## Am I capturing my visitors?

Machinery health, not behavior. The measure is **arrivals ÷ births** — of the recordings that started (`slice_started`), how many landed (distinct slices in R2: `locus ls` over the date partitions the window spans, rows filtered on their open time). Both planes carry the same client-minted start clock, so window both sides on it. One scoping the LIST cannot do is the recorder era: arrival keys carry no version, so a window spanning a deploy mixes eras in its numerator — era questions read loaded content, where every event carries `script_version`.

A ratio cannot be interrogated, so **join instead**: birth rows and arrival rows carry the same snippet, visitor, and slice, and the join hands you the actual set of births that landed nothing — how long those visitors lived, what their devices reported, what faulted, which browser. The worker stamps every datapoint with what the transport attested about its sender — the request's origin, user-agent, and network AS organization, at the uniform positions telemetry-schema.json declares — so the never-delivering cohort has a device identity to group by even though the chunks that would have carried one never came.

The join has two shapes. A window — every birth against everything that landed — lists the day partitions the window spans once and filters the rows. A named cohort — the visitors behind a fault class, a burst, a suspect network — is one `locus ls snippet/day/visitor/` per visitor, under the day its slice opened on the device's clock; a context that lives across midnight files its later slices under the next day.

The join costs you two things. Births are **sampled**, so enumerated rows undercount: a rate uses `sum(_sample_interval)`, while the joined set is a sample of the population. And chunks land *later* than a slice opens, sometimes days later, so a fresh birth with nothing in R2 may be in transit rather than lost — the arrival row's `last_upload_ms` against its `open_ms` tells you which, and ageing births out until the loss curve flattens finds the horizon past which "in transit" stops being an answer. An arrival with no birth row is a birth whose ping died; the context's history reads off the arrival's open-to-upload lag and its later `cost_sample` rows.

Habits that break the join: it is only as fresh as its arrivals listing — re-list before believing a miss. Arrivals join on upload time, never partition date: a returning visitor's new page ships whatever its device still holds, and those old-stamped slices file under old partitions, so "birthed this window, nothing in this window's partitions" is not "delivered nothing". And loss is a visitor-level verdict: a per-slice join counts recordings still waiting on their devices as missing. A returning visitor also carries old cost rows: a cost or delivered figure read without the page context's own time window attributes an old visit's delivery to the new one.
The gap is mostly not loss:
- **Bounces.** A visitor gone within seconds ends the page before its recording can ship; it waits on their device and lands only if they return. Expected and permanent — it measures how bouncy the traffic is, not the machinery's health. In the db a bounce is a one-chunk slice of a few hundred bytes (the hidden marker) filed `discarded: no snapshot`, with its session row; its `page_load` ping says the DOM was captured before the page ended.
- **Nothing to send.** A page can die before the recorder has a DOM worth capturing: it births, but with no snapshot there is nothing replayable to ship. Countable exactly — first-slice births against full-load (not SPA-route) `page_load` pings over the same window. It is the reach of the script minus the reach of the recording, and it climbs with anything that delays capture (a slow page, a heavy `<head>` tag).
- **In transit.** Delivery is deliberately patient: recordings arrive hours or days late from offline devices, backgrounded tabs, and return visits, so a recent window's ratio climbs as they land.
- **Crawlers.** A JS-executing crawler that passes the gate births a fresh identity, lives under the first drain tick, and delivers nothing — a hosting network's fleet can run hundreds of identities a day on one site, sinking the ratio for everyone. Cut them by announced user-agent and by shape before reading it.
- **Genuine loss announces itself by name — never infer it from the ratio.** The loud signals: `upload_rejected` is the store refusing bytes. `worker_error` is ingestion itself failing — though an edge answering in the worker's place (a gateway 504) kills the request before the worker runs and writes no `worker_error`, so the recorder's own drain fault is that failure's only witness. `chunk_oversize` is a page too heavy to store. `recorder_fault` is the recorder unable to do its job on that device. It carries the verbatim error, the address of the page it happened on, and a reason naming what failed: starting up, capture itself throwing inside rrweb's observers, the buffer it writes captured events into, the loop that delivers them, a batch given up on after too many attempts, records evicted at the backlog ceiling, the SPA route detection whose failure silently costs `page_load` pings, or the recorder shutting itself down after too many errors. A start-path fault comes before any slice or birth exists, so it joins to nothing; locate it by the fault's own address and the worker-stamped origin. There is also `chunk_errors` in a loaded events.db: the recorder's whole error log, shipped inside the chunks it did deliver. Send failures whose batches later landed sit in it right beside genuine drops, so loss there is only the records that state a loss (a drop, an eviction), and you read them one by one — the rows share no unit (a drop record can stand for a whole batch, a retry record for no loss at all), so no count over them measures anything. Expect the announcement itself to go missing. The fault fires at the hostile moment that produces the drop — a frozen tab's unfreeze, a dying page — so it often dies with it. The plane it rides samples. The shipped log is capped on the device and only lands when a later chunk delivers. So read a drop across both channels and expect either to be missing. The two channels are independent: faults ride telemetry, not the chunk path, so a device that delivered nothing can still tell you why — the one case `chunk_errors` can never cover. A reason fires once per page context however often it recurs there, so a fault count is contexts, not occurrences. Two quieter tells: a `cost_sample` context whose peak backlog climbs while delivered bytes stay 0 is holding a recording it cannot ship, and an engaged, multi-page session missing slices in the middle is a shape bounces cannot explain.

The bounce explanation fits any number, so test it against lifetime. Bounces are short: their cost stream shows seconds of foreground time and no `page_load` beyond the first. A lost recording whose page context lived minutes, ran the drain loop, and shipped nothing is not a bounce. Split the gap by page-context lifetime before explaining it, and check that window's faults.

A storm of one fault across many visitors is a crawl until proven an outage: fresh single-fault visitors with no other telemetry ever, disjoint from recorded traffic, is a crawler fleet whose environment kills that path on every visit; known recorded visitors faulting is a real outage; births holding cadence through the storm confirms the former.

Upstream of every birth sits the bot gate, and it attests itself: a page context BotD declined emits `capture_gated`, carrying which detectors fired. The rows are the gate's verdicts, not a census of bots. BotD is a set of headless-environment heuristics, and a modified real browser — an in-app webview especially — can trip one, so a gated share of real traffic on residential networks is a false-positive question before it is a bot count. The detail, user-agent, and network stamps are how you audit that, and the sharpest tell is one cookie both gated and recording: a state-dependent check flickering on a real device. So "how much of my traffic is bots" reads off the rows as an estimate three times over — sampled, a floor (a device whose telemetry path is blocked gates invisibly), and only as honest as the verdicts. A gated page context never births and belongs in no completeness denominator. That cuts both ways: a gate false-positive is traffic silently unrecorded, invisible everywhere but these rows. A rollout gate's exclusion needs no ping — its fraction is written in the facade, so what it excluded is arithmetic over births and that fraction. Out of scope entirely: visitors the script never ran for (ad-blocked, gone before the fetch) leave no ping to count, so only the operator's own traffic data — server logs, a CDN's request counts — can be that denominator. And whether the replay *looks* right is fidelity, a render-time matter, not an arrival count.

## Sessions, engagement, and bounce

Read the definitions file first; its defaults hold until the operator adjusts them. Sessions, engaged, and bounce are counts over the `sessions` table in the loaded db, so a bounce-rate question is a load of the window's partitions and a query — scoped by `snippet` and `start_ts`, cut by a join to `slices` for the device or the host, or to `events` for what happened inside. Telemetry cannot produce one: the definition runs on user events, which the pings do not carry, over rows the sampler drops, so nothing assembled from pings estimates a session. A rate question in this vocabulary always reads the db.

What telemetry does answer in this vocabulary, as weighted sums per visitor and per page:

- **Visitors over a period** — how many, how many came back, how many ever reached a page — is one AE query grouped by visitor (`if()` inside the aggregates, `HAVING` for the membership), with no session boundary in it: the whole population the script ran for, bounces and never-returners included, sampled.
- **Pageviews** are `page_load` pings — one per full load and one per route change, flagged apart, each carrying url and referrer (which is also the traffic-source cut). Every url on this plane, referrer and fault url alike, is an address — origin, path, and fragment; the recorder drops the query string before it is on the wire. So a cut on this plane is a cut on paths and hosts: campaign and click-id params are not here, and a question that turns on one is a content read, where the recording keeps each arrival whole. A pageview fires only when the address changes — path or fragment (`recorder/src/route.js`) — so a step that happens in place is not on this plane at all: a cart drawer, a modal, an in-page form, a checkout on another domain. A funnel read from pageviews shows such a step as zero with full confidence; the step is in the clicks and mutations the recording holds.

**Conversion** is not a definition and is never read off a path. What converting means comes from the site's business frame in `data/context/<snippet>.md`. From that meaning, derive a structural signature for this site — the pages reached, the inputs made, in what order, inside one session — and calibrate it against a few sessions by looking (a replay, or an analysis) until it holds. Then the count is a query over `events` joined to `sessions`, and only a session the acts don't decide gets read. The rate is those sessions over the table's sessions in the same window, both counts named.

Every count here carries known biases. Carry each with its direction:

- Counts on telemetry are estimates under sampling: weight them and say "about". Counts over the db are exact — exact about what loaded — so when the two meet, say which is which.
- A count over recordings counts recorded sessions. A page that dies before its first drain tick still ships its hidden marker, so a bounce is there — one page load and nothing after — and a visitor whose slices arrive days later is there once they do. Not there: a device whose marker the network ate and that never came back, and the part of a visitor's history outside the loaded range.
- Counts are of the visitors the facade admits. Read the facade the store vends (`recorder/src/global.js`) for a rollout gate before giving any count: under one, every visitor, session, and pageview figure covers the admitted share, and the site's total is that figure over the fraction — say which one you are giving.
- A visitor's identity is a cookie. A browser that refuses to keep one turns the same person into a stranger on every page: one episode on the site counted as several one-page sessions, each in the bounce numerator, in a shape identical to genuine bouncing. The visitor's birth row on telemetry says how the recorder came by the identity, so those sessions can be cut by a join on the visitor. A browser that shortens a cookie's life instead of refusing it fragments the same way across days, and no birth can see that coming.
- Crawlers that execute JS and pass the bot gate record like visitors — fresh identity, one deep pageview with no referrer, gone in seconds — and land in the session count and the bounce numerator. Two ways to cut them. By fact: a crawler that announces itself does so in the user-agent the worker stamps on every telemetry row, joined by visitor. By shape, for the ones that announce nothing: a burst of single-page "visitors" seconds apart, each direct to a different deep URL; or a network whose every visit is a fresh cookie and one pageview, at the same steady rate day after day. The network name stamped beside it corroborates and never decides — privacy relays egress ordinary phone traffic through datacenter networks, so a cut on the network alone discards real visitors. Past those two cuts the residue is invisible by construction: a bot faithful enough leaves a visitor's every trace. Visitor, session, and bounce counts carry an inflation you can acknowledge but never remove — say so when the number matters.

Answer in the operator's vocabulary with the definition named — "by your definition (engaged = longer than ten seconds, or more than one page), 370 recorded sessions this week, 41% engaged, bounce 59%" — so the definition stays visible and adjustable.

## What is it costing?

Cloudflare exposes metered usage, not dollars (the invoice is account-level and billing-scoped), so compute it: **usage × published rate − free tier.** The antecedents:
- R2 storage (GB-month): `r2StorageAdaptiveGroups`, integrating stored bytes over the period.
- R2 operations: `r2OperationsAdaptiveGroups` by `actionType` — Class A (Put/List) vs Class B (Get).
- Worker requests: `workersInvocationsAdaptive` (uploads + telemetry; static-asset vends are a free class and never appear here).
- Model spend: the deployment's own ledger. Every billed model call lands in `spend.jsonl` beside the db as dollars (persisted usage × the card's declared prices), and the spend block of `locus status` sums it per UTC period against any declared caps. The persisted transcripts behind each entry carry the per-call usage.

Rates and free-tier limits come from the Cloudflare R2 and Workers pricing pages and the model's pricing page.

**Per visitor,** storage and model spend are exact — the visitor's rows in `locus ls`, bytes summed, and the persisted transcripts that carry the visitor. Worker requests have no per-visitor dimension, so per visitor is total ÷ visitor count: an average, and negligible regardless.

**Projecting forward** is usually the real question — "will my traffic break the free tier, and what do I do." Three meters can bind, and the traffic's shape picks: storage and Class A writes track how long page contexts stay open, while telemetry pings track how many open — so traffic of long-lived tabs meets R2's meters first, and traffic of many short page contexts (bouncy, bot-ridden) can meet the Workers free plan's daily request cap first, which fails closed rather than billing. AE never binds. Which one is your own arithmetic: daily chunk bytes × retention horizon against the storage tier, monthly PUTs against the write tier, daily uploads + pings against the request cap (`store/README.md` carries the horizon and the storage rate; write rates and free-tier ceilings come from the Cloudflare pricing pages).
- **Storage is bytes × horizon.** Steady state = daily chunk bytes × `retention_days`. The lever is the horizon — which is also how long recordings are kept at all, in the bucket and in the local db alike.
- **Writes are cadence-bound, not volume-bound.** One R2 Class A write = one chunk stored, and each drain ships whatever accrued that interval, however little — so an active page context writes roughly once per drain interval regardless of data volume, and most chunks sit far below the size cap. Write count ≈ fleet open page-context time ÷ drain interval: it tracks **how long tabs stay open**, not headcount and not bytes. One visitor parking a tab open all day out-writes a hundred bouncers, so a per-visitor average understates the ceiling risk; the distribution is heavy-tailed, so project off the tail of the deployment's own per-visitor write distribution.
- **The write lever is the drain cadence** — the recorder's interval/ramp configuration, capture config in the vended facade (`recorder/src/global.js`; edit and redeploy the store). Raising it costs delivery latency only (capture is durable in IndexedDB on emit, and a busy page context's backpressure still drains it promptly), plus a wider never-return window late in quiet page contexts. The chunk size cap is not a write lever: real chunks rarely approach it, and it bounds per-chunk blast radius.

## Is it harming the site or visitors' devices?

Read the `cost_sample` distribution: main-thread time, bytes pushed to the sink, bytes the sink acknowledged, the per-context heap **max**, the heap **limit** (the tab's OOM ceiling), and the peak on-device **buffer backlog**.
- **Main-thread time is a floor.** The timer starts when rrweb hands the recorder an event (`recorder/src/index.js`) and covers stamping, the buffer write, and chunk serialization; rrweb's own observation and DOM serialization run before it and are never counted. On a view that mutates heavily the uncounted half can be the larger one, so the figure bounds what the recorder adds on top of rrweb, not what capture costs the page.
- **OOM proximity is the ratio, not the raw heap.** Ceilings differ wildly by device (desktop Chrome ~4GB, mobile far lower), so the device-independent signal is `heap max ÷ heap limit` *per data point*; aggregate those ratios across the fleet, where a distribution climbing toward 1.0 is the OOM-risk trend. Never pool the raw limit — it is a per-context constant, not a quantity.
- **Backlog is the off-heap storage signal.** The peak outbox+inflight bytes the buffer held is pressure the heap figure misses — the buffer lives outside the JS heap — and it climbs when delivery stalls (offline, slow network).
- **Upload bytes are what the device spent, not what arrived.** They count bytes handed to the sink: a retried batch spends them again, a failed upload spends them for nothing. Delivered bytes are the acknowledged half — the batches the drain loop shipped and the store answered. The page-hide shot that carries a bounce's recording is fire-and-forget and never counted, so a context reading zero delivered bytes can still have landed. Read spent as bandwidth cost and acknowledged as proof of delivery — and neither as completeness, which is the R2 join.
- **`snapshot_fatal` is the catastrophe signal:** a page whose first snapshot was too heavy to store, so the recording could never replay and the recorder stopped itself — the page context that recorded nothing at all. Any organic instance outweighs every distribution.

Three limits bound the answer:
- **Heap is Chromium-only** (`performance.memory`) — Safari and Firefox have nothing to measure, and unmeasured lands as the worker's UNMEASURED sentinel (telemetry-schema.json declares its value), max and limit alike. Exclude rows whose heap limit is not a positive number before computing the ratio. Backlog is cross-browser, being the recorder's own bookkeeping rather than a `performance` API, and carries the same sentinel when the buffer never answered — which is not an empty buffer.
- Heap and backlog are **sampled maxes**, so a spike between samples is missed.
- The harm answer is about the device *fleet*; one machine's distribution says nothing, and it becomes real only once varied real devices send data. On a single box you validate the instrument, not the answer.

## Am I leaking PII?

Not a telemetry question — it is the captured content against the masking config. The config is the facade the store vends (`recorder/src/global.js`); what to audit is the stored content, post-masking, exactly as it landed. Audit by reading: load slices from the pages where sensitive input or content occurs and read what the visitor's screen held — the projections, and the screenshots when a doubt needs pixels — flagging anything sensitive that landed.

For credentials, read every input value on the login, sign-up, and reset pages, not just the values of password-typed fields. The credential mask decides per element from what its markup says (`recorder/src/masking.js`), and a show-password toggle that re-renders the field as a bare `type=text` with no credential token in its name or autocomplete records the secret verbatim — so the leak, when there is one, sits in a field the type never marks. Masking leaves only asterisks; a value on those pages that is not asterisks is the thing to look at. And not every input value arrives by a visitor's typing: marketing scripts write what they already know into the page's inputs — a subscriber's email into an unnamed, untyped field — so an audit reads every input value on the loaded pages, not only the fields visitors touched or the markup declares sensitive. A scan clears the slices it read, never the corpus: it is a sample, and what masking already withheld never existed to find. One cheap standing detector on the rates plane: scan `page_load` urls for pages where sensitive input could occur — a checkout or an account page appearing there says a maskable session may now exist to audit.

A leak found is permanent for the recordings that carry it — masking is record-time and irreversible — so the remedy is two moves: fix the rule in the facade and redeploy, which changes future recordings only, and then decide when the leaked recordings go. The horizon takes every copy of them — the bucket's and the db's — on its own; sooner than that is the deletion recourse the change-deployment skill states.
